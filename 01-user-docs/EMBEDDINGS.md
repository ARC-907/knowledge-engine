# Embeddings — Semantic Search

Knowledge-Engine's default search is **FTS5**: fast, lexical, keyword-based. It
matches the words you type. For most corpora that is enough.

The engine also ships an **opt-in semantic search layer** — embeddings — that
matches by *meaning*. Ask for "how to make decisions under pressure" and it can
surface a file about the OODA loop even if those exact words never appear.

The two are independent. Use FTS5, embeddings, both, or neither.

## When you want embeddings

| Use FTS5 (the default) when… | Add embeddings when… |
| --- | --- |
| You search with known terms | You search with paraphrases / concepts |
| Your corpus is small to medium | You want "find similar" / "find by topic" |
| You want zero extra dependencies | You can run a local embedding model |
| You want instant, deterministic results | Some retrieval latency is acceptable |

Embeddings are not a replacement for FTS5 — they're a second retrieval mode.
Many setups query both and merge.

## What you need

Embeddings are generated by an **Ollama** embedding model running locally.
You need:

1. **Ollama installed and running.** Get it from <https://ollama.com>.
2. **An embedding model pulled.** The default is `bge-m3`:
   ```
   ollama pull bge-m3
   ```
   `bge-m3` is a strong multilingual embedding model with a large context
   window. Any Ollama embedding model works — set `KE_EMBED_MODEL` to use a
   different one.

No cloud API, no keys. Embedding generation stays on your machine.

## Building the index

The embedding index is built by a module in the engine — separate from the
FTS5 index, written to its own SQLite database.

```pwsh
# (optional) choose the model — defaults to bge-m3:latest
$env:KE_EMBED_MODEL = "bge-m3:latest"

# full build
python -m knowledge_engine.embeddings.build

# incremental — only re-embed files that changed
python -m knowledge_engine.embeddings.build --incremental

# show index statistics
python -m knowledge_engine.embeddings.build --stats
```

The builder walks every markdown file under the corpus root, splits each into
overlapping ~1500-character chunks, embeds each chunk via Ollama, and stores
the chunks plus their embedding vectors in SQLite.

A first full build over a few thousand files takes a while — it's one Ollama
call per chunk. After that, `--incremental` only touches changed files and is
quick.

## Searching

```pwsh
# top 10 semantically-closest chunks
python -m knowledge_engine.embeddings.search "your query"

# control how many hits
python -m knowledge_engine.embeddings.search "your query" --top 5

# restrict to one top-level corpus subdirectory
python -m knowledge_engine.embeddings.search "your query" --library libraries
```

The search command embeds your query with the same model, compares it against
every stored chunk by cosine similarity, and returns the closest ones ranked by
score.

## Configuration

All embedding settings come from environment variables with sensible defaults:

| Env var | Default | Purpose |
| --- | --- | --- |
| `KE_OLLAMA_URL` | `http://127.0.0.1:11434` | Where Ollama is listening |
| `KE_EMBED_MODEL` | `bge-m3:latest` | The embedding model to use |
| `KE_CORPUS_ROOT` | `./corpus` | Which corpus to embed |
| `KE_EMBEDDINGS_DB` | `$KE_DATA_DIR/embeddings.db` | Where the embedding index is stored |

Set them before running `build` or `search`. They are read at process start.

## How it relates to the rest of the engine

- The **FTS5 index** (`engine/data/index.db`) and the **embedding index**
  (`engine/data/embeddings.db`) are separate databases. Building one never
  touches the other.
- The dashboard and the MCP `search` tool currently use **FTS5**. Embeddings in
  v1.0 are a CLI / library capability — `knowledge_engine.embeddings.search` is
  importable, so you can wire it into your own code or a custom route.
- Keeping them separate is deliberate: the lean core has no Ollama dependency,
  and embeddings are a clean add-on you switch on when you want it.

## Keeping the index fresh

The embedding index does not auto-update. After you add or edit corpus content:

```
python -m knowledge_engine.embeddings.build --incremental
```

Run it on whatever cadence fits — manually after big edits, or on a schedule
for an actively-growing corpus.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| `No embedding index at …` on search | Run `python -m knowledge_engine.embeddings.build` first. |
| Build hangs or errors immediately | Ollama isn't running, or isn't at `KE_OLLAMA_URL`. Start it; check the URL. |
| "model not found" | Pull the model: `ollama pull bge-m3` (or whatever `KE_EMBED_MODEL` names). |
| Build is very slow | Expected on first full build — one model call per chunk. Use `--incremental` after. |
| Results feel off | Different embedding models suit different content. Try another model via `KE_EMBED_MODEL` and rebuild. |
